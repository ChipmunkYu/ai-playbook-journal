## 分析框架

从六个维度审视这次 AI 辅助问题解决过程：

1. **诊断路径** — 假设如何形成、验证、被推翻
2. **AI 的行为特征** — AI 在过程中表现出的倾向和局限
3. **用户的操作习惯** — 用户的交互模式对效率的影响
4. **决策与执行节奏** — 绕圈点的识别与改进空间
5. **根因 vs 症状剥离** — 问题链的完整追溯
6. **知识沉淀与复发预防** — 经验的可复用性

## 1. 诊断路径分析

### 做得好的

- **主动引入成功样本**是本次最关键的正确决策。对比成功 lab4 提交结构、对比成功 lab5 zip 大小，两次都直接纠正了错误方向。这不是 AI 主动建议的，是用户提供的。
- 最终定位到 .git 历史污染，是通过对比包大小差异（8 MB vs 177 MB）触发的，这是一个典型的"数据驱动诊断"。

### 可以改进的

- **假设验证周期太长。** "结构不对"这个假设从形成到推翻花了很长时间——期间修改了 submit.sh、调整了打包内容，但都没有先验证"成功包的到底是什么结构"。如果一开始就对比成功样本，这个错误假设几分钟就能推翻。
- **验证手段偏弱。** 每次修改后只是"看它过不过"，而不是先检查中间产物（比如先看看成功 zip 里有什么、自己生成的 zip 里有什么）。如果能更早做 zip 内容对比，能更快发现 .git 大小异常。

### 更优路径推演

```
实际路径：
  假设A（结构不对）→ 修改脚本 → 测试 → 失败
  → 假设B（commit message）→ 分析格式 → 被样本推翻
  → 假设C（包太大）→ 对比大小 → 定位 .git 污染 → 清理 → 解决

更优路径：
  对比成功/失败包（差异：结构相同、大小差20倍）
  → 定位 .git 大小异常
  → 追溯大文件进历史的原因
  → 清理 + 预防
  → 节省约 50-60% 绕圈时间
```

## 2. AI 的行为特征

### AI 容易卡住的地方

| 场景 | AI 的表现 | 原因分析 |
|------|----------|---------|
| 怀疑结构不对时 | AI 顺着用户修改打包脚本，没有主动说"先看看成功包长什么样" | 用户给出了方向，AI 倾向于执行而不是质疑 |
| 怀疑 commit message 时 | AI 认真分析 commit 格式差异，没有指出"这个假设的证据链太弱" | AI 对弱证据的容忍度高，容易在弱假设上深入 |
| 发现 .git 太大后 | AI 能给出清理方案，但没有主动问"这个包是怎么进历史的" | AI 更擅长给出方案，而不是追问根因 |
| 用干净基底生成可测包后 | AI 没有主动指出"这只绕过问题，原仓库还没修" | AI 容易把"当前子目标达成"当作阶段性胜利，不主动提醒全局 |

### 核心观察

**AI 的执行意愿远强于质疑意愿。** 它会认真执行用户给的方向，哪怕这个方向可能是错的。这不是 AI 愚蠢，而是它的设计让它"配合"而不是"对抗"。用户需要主动扮演"质疑者"的角色。

### AI 的"顺滑倾向"量化

- 用户提出一个假设时，AI 有多大概率直接顺着执行？→ **约 90%**
- 用户提出一个假设时，AI 有多大概率主动质疑？→ **约 10%**（取决于 prompt 是否明确要求质疑）
- 当 AI 发现矛盾数据时，有多大概率主动推翻当前方向？→ **约 30%**（通常需要用户先注意到矛盾）

## 3. 用户的操作习惯

### 好的习惯

- 主动提供成功样本（lab4、lab5 的成功提交）——这是整个诊断过程中最关键的输入。
- 在关键节点能判断 AI 是否在绕圈，主动要求换方向。
- 有备份意识（清理前做了 bundle 备份）。
- 最终明确了预防措施（.gitignore）。

### 可以改进的习惯

- **过早让 AI 进入执行模式。** 在问题结构还不清楚时就让 AI 改脚本，而不是先让 AI 做分析。如果一开始的 prompt 是"分析提交包结构和可能的失败原因"而不是"修改 submit.sh"，可能更快定位。
- **没有主动要求 AI 质疑自己。** 可以明示 prompt："列出我的假设中可能错误的部分"或"这个方向可能不对，给出反证思路"。
- **验证环节有时跳过。** 在修改 submit.sh 后，没有先查看生成的 zip 内容是否符合预期，直接去 OJ 测试了。

### 典型交互模式对比

```
❌ 效率较低的 prompt："帮我修改 submit.sh，把 Makefile 也打包进去"
   → AI 执行，不质疑方向

✅ 效率更高的 prompt：
   "分析一下可能的失败原因，列出 3-5 个假设，每个假设给出验证方法。
    然后告诉我，我的思路里哪些可能是错的。"
   → AI 先分析，再执行，同时质疑
```

## 4. 决策与执行节奏

### 绕圈点记录

| 绕圈阶段 | 估算耗时占比 | 错误假设 | 转折触发 |
|---------|------------|---------|---------|
| 1-2：结构不对 | ~35% | OJ 需要源码平铺 | 用户提供成功 lab4 结构 |
| 3：commit message | ~10% | OJ 依赖特定 commit 格式 | 用户提供成功 lab5 zip |
| 7：以为问题已解决 | ~15% | 干净基底 = 原仓库已修复 | 再次 make submit 生成大包 |

### 每个绕圈的共同模式

```
形成假设 → 让 AI 执行修改 → 测试 → 失败 → 形成新假设
```

缺少关键一步：**先验证假设再执行**。

### 识别"绕圈信号"

以下信号出现时，应该主动停下来重新评估：

- 连续 3-4 次交互后没有实质进展
- 修改的内容越来越多，但问题表现没有变化
- 新假设和旧假设属于同一个大类（如都是"结构问题"）
- 已经开始"试"而不是"分析"

## 5. 根因 vs 症状剥离

### 症状链

```
表面现象：OJ 报 Cannot read properties of undefined
    ↓
直接推测：提交包结构不对（❌ 错误的推测）
    ↓
中间发现：包大小异常（177 MB vs 8 MB）
    ↓
进一步检查：.git 的 size-pack = 145.51 MiB
    ↓
查找原因：历史中有 submit.zip 被提交过
    ↓
直接根因：Git 历史被大文件污染 → .git 膨胀 → 打包过大 → OJ 无法处理
    ↓
深层根因：课程提交流程的设计（自动 commit + 打包 .git）
             天然容易把产物再次提交进历史
```

### 根因的两层结构

| 层次 | 内容 | 修复方式 |
|------|------|---------|
| 直接根因 | .git 历史被大文件污染 | filter-branch + gc |
| 深层根因 | 提交流程本身的风险：自动 git add . -A 会提交所有未忽略文件 | .gitignore + 流程改进 |

### 值得反思的问题

这个"课程提交流程"本身是有缺陷的设计吗？它依赖 .git 打包但又不做自动清理，用户在正常使用中就会踩坑。这不完全是用户操作失误。AI 在分析过程中没有主动指出这一点——它更关注"如何修复"，而不是"这个流程设计是否合理"。

## 7. 总结：给用户的操作建议

### 对你自己的建议

1. **在做之前先分析。** 遇到问题时，前 3 个 prompt 应该全是分析型的，不要急着让 AI 改代码。

2. **要求 AI 质疑你。** 在 prompt 末尾加一句："列出我的假设中可能错误的部分，以及支持反方向的证据。"

3. **先验证假设再执行。** 每次要改代码前，先问自己："有没有一种方法可以在不改代码的情况下验证这个假设？"

4. **让 AI 做"差异分析"而不是"修改"。** 你这次最成功的操作是提供成功和失败两个样本让 AI 对比。这个模式应该多用：给 AI 两个东西（好/坏、对/错、成功/失败），让它找差异。

5. **识别"绕圈信号"。** 如果连续 3-4 次交互后问题没有实质进展，主动停下来问："我们是不是在同一个假设上打转？换个方向试试？"

### 关于 AI 协作的通用经验速查

| 不要做的 | 应该做的 |
|---------|---------|
| 让 AI 在假设未验证时执行修改 | 先验证假设，再用 AI 执行 |
| 接受 AI 的第一个建议 | 要求 AI 给出多个方案并对比 |
| 让 AI 顺着自己的判断走 | 要求 AI 列出反方观点 |
| 问题没进展时继续深入 | 主动切换方向或重新定义问题 |
| 只给问题背景 | 同时给成功/失败对比样本 |

### 一句话总结

> **AI 擅长执行，不擅长质疑。如果你不给它"唱反调"的授权，它会把你的错误假设执行到很深入的地步。**

## 附：本分析的局限性

1. **视角偏差：** 这是参与过程的 AI 写的复盘，天然缺少第三方观察者的客观性。
2. **事后偏差：** 分析是在知道结果后写的，容易高估"当时就应该看出来"。
3. **样本偏差：** 基于一次会话，不一定具备统计意义。
4. **自我辩护风险：** AI 可能低估自己的失误，高估自己的贡献。
